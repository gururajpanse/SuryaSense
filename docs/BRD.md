## 2. Executive summary

This project delivers, by 12 Oct 2026 and by one person, an automated pipeline that detects solar flares in Aditya-L1 soft and hard X-ray data, estimates the probability of a flare in the next 30 minutes, and shows both on a live dashboard with visual alerts.

The system has two operating modes, because Aditya-L1 data on PRADAN arrives as daily or 12-hour files and is not a live stream. **Replay mode** runs the full Aditya-L1 pipeline (SoLEXS plus HEL1OS) over past days and validates it against the GOES flare list. **Live mode** runs on the GOES real-time X-ray feed with a model trained on GOES history, so the evaluator can watch alerts appear during the demo.

Success means measured and honestly reported results: true positive rate, false alarm rate, True Skill Statistic and lead time in minutes, split by flare class. A negative result, such as an advanced model that does not beat the baseline, is an acceptable and reportable outcome. Nothing here is an operational warning system.

## 3. Background

### 3.1 Why flares matter

Solar flares are sudden bursts of radiation caused by the release of magnetic energy in the solar atmosphere. They can disturb satellite communication, GPS navigation and power grids. Early detection (nowcasting) and early warning (forecasting) help protect infrastructure.

### 3.2 Aditya-L1 data

ISRO's Aditya-L1 observes the Sun from Lagrange Point L1. Two of its X-ray instruments are used here: SoLEXS (soft X-rays) and HEL1OS (hard X-rays). Both are published as Level-1 data through the ISRO ISSDC PRADAN portal.

| Fact (checked on PRADAN screenshots, 4 Oct 2026) | SoLEXS Level-1 | HEL1OS Level-1 |
| --- | --- | --- |
| Number of files | 843 daily files | 2,745 files |
| File name pattern | AL1\_SLX\_L1\_YYYYMMDD\_v1.0.zip | HLS\_YYYYMMDD\_HHMMSS\_\<seconds>sec\_lev1\_V111.zip |
| Typical size | about 2.4 to 2.9 MB per day | about 49 MB per 12-hour chunk (2026) |
| Latest listed | 1 Oct 2026 | 3 Oct 2026 |
| Contents (from public documentation) | Soft X-ray light curves | OGIP-style FITS light curves at 1 second cadence in several energy bands, plus 20 second spectra |
| Known gaps | Some days missing, for example 22, 23 and 28 Sep 2026 | Not yet checked |

In May 2024, HEL1OS shows about 200 rows of roughly 200 MB each, about 40 GB for one month. For this reason 2026 is the main dataset.

### 3.3 GOES as ground truth

GOES X-ray sensors give the standard flare classes (A, B, C, M, X) based on peak flux. The project uses the NOAA NCEI GOES XRS flare summary (xrsf-l2-flsum) and 1-minute flux (xrsf-l2-avg1m) for labels and validation. In replay mode GOES is never a model input. Whether science-quality 2026 GOES files exist is **UNVERIFIED**.

### 3.4 Project context

The project is a semester mini project for a team of three. One member does all the work. The professor or evaluator will see a live dashboard demo. The work follows an AI SDLC and uses Google Antigravity as the coding agent, controlled by an AGENTS.md rules file.

## 4. Problem statement

The project team has no automated tool that reads both Aditya-L1 X-ray bands, finds flares in them, predicts the next flare and shows the result visually. Other public projects exist, but their results are not treated as ground truth here.

| Catalogue | None for the project | Queryable catalogue regenerated by one command |

| Validation | None | Matching against the GOES flare list with TPR, false alarm rate, TSS and per-class results |
| Visualisation | None | Dashboard with light curves, alerts, replay mode and live mode |
| Reproducibility | Ad hoc scripts | Config-driven pipeline, tests, CI and Docker |

## 9. Business rules

| ID | Rule |
| --- | --- |
| BRU-01 | Train, validation and test splits are chronological. Random splitting is never used. |
| BRU-02 | A 60-minute embargo gap separates the splits. |
| BRU-03 | Background estimates use trailing windows only, never centred windows. |
| BRU-04 | Thresholds and hyper-parameters are tuned on validation data only. |
| BRU-05 | The test set is scored once. Any further change after seeing test results is reported as such. |
| BRU-06 | In replay mode GOES is used for labels and validation only, never as an input to the Aditya-L1 model. |
| BRU-07 | In live mode GOES is the model input. The live model is trained only on GOES data from periods before the test and demo periods (proposed rule, to be confirmed in the PRD). |
| BRU-08 | Headline metrics are TPR, false alarm rate, precision-recall and TSS. Accuracy is never the headline for a rare-event problem. |
| BRU-09 | Negative or weak results are reported honestly. |
| BRU-10 | The system is never described as an operational warning system. |
| BRU-11 | Dates 2024-07-26, 2024-09-01, 2024-10-02 and 2025-02-20 are excluded (reported duplicated SoLEXS days, not verified by the project). |
| BRU-12 | Raw PRADAN data is never pushed to a public repository. ISRO and ISSDC are cited. |

## 10. Operating scenarios

### 10.1 Offline build (done once per data change)

1. Download the chosen Aditya-L1 days and GOES files into the read-only raw folders.
2. Build the manifest and the coverage report; check the SoLEXS and HEL1OS overlap.
3. Read each instrument into a clean time series.
4. Detect flares in each band and merge into the master catalogue.
5. Validate the catalogue against the GOES list.
6. Build labels and trailing-window features, train the model ladder, tune on validation, score the test set once.
7. Save models, metrics, figures and the model card.

### 10.2 Replay demo

1. The evaluator picks a past day (Aditya-L1) in the dashboard.
2. The dashboard plays the light curves at an adjustable speed.
3. Nowcast detections and forecast probabilities appear as the replay moves, with alerts.
4. GOES flares are shown alongside so the evaluator can compare.

### 10.3 Live demo

1. The back end polls the GOES real-time X-ray feed about every minute.
2. The GOES-trained model computes the 30-minute flare probability.
3. The dashboard updates the light curve and shows an alert when a flare is nowcasted or the probability crosses the tuned threshold.
4. If the feed fails, the dashboard switches to a recorded GOES sample and says so on screen.

## 24. Glossary

| Term | Meaning |
| --- | --- |
| Nowcast | Detect a flare that is happening now |
| Forecast | Estimate the probability of a flare in the next 30 minutes |
| SoLEXS | Aditya-L1 soft X-ray spectrometer |
| HEL1OS | Aditya-L1 hard X-ray spectrometer |
| GOES XRS | NOAA GOES X-ray sensor, used for flare classes and ground truth |
| TPR | True positive rate, the share of real flares detected (recall) |
| False alarm rate | Share of alarms that were wrong, as defined in the PRD |
| TSS | True Skill Statistic, a score for rare events that is not inflated by many non-flare periods |
| Lead time | Minutes between the first alert and the flare peak |
| Embargo | Gap between train, validation and test periods to stop leakage |
| Leakage | Information from the test period or the future getting into training |
| PRADAN | ISRO ISSDC data portal for Aditya-L1 |
| MoSCoW | Priority labels: Must, Should, Could |
